# Changelog

## Unreleased

- [SECURITY] The Windows release environment gate is harder to fool with the tree as it stands. The reviewer count is read with the error output kept apart from the payload and compared as a number, so a warning `gh` writes to stderr on a successful call can no longer turn "the environment names no reviewer" into a pass. The wiring check recognises a publishing job by what it does, not only by the commands it happened to know: a job that publishes with `gh release edit`, with a line continued command or with a path split across quotes is a publishing job, and so is a job that delegates to a release-publishing action or that can write to the repository at all — the last one catches a publisher the check cannot see inside, such as a script in the repository or a reusable workflow. Every publishing job has to declare its environment and run the gate. The environment the gate checks is read from the gate step itself rather than from anywhere in the job, so a decoy step cannot stand in for a gate step that checks a different environment. The check accepts the legitimate shapes it used to reject — the object form of the `environment:` key, a quoted environment name and a quoted `continue-on-error: "false"` — and it reads only the workflow files themselves, not the copies it makes of them while it proves itself. The publish step checks the release tag once more before it creates the release, because `gh release create --target` is ignored when the tag already exists. `scripts/check-release-environment-gate.sh` drives the gate against the recorded responses the environment API can answer with, so the gate itself cannot rot into a script that always says yes.

- [FIX] The signed Windows tester release can now update a release it already published, which is what its own input promises. The publish step only knew how to create a release, so a re-dispatch — a repaired or re-signed build under the same tag — failed with "already exists" and left the old assets in place. It now replaces the assets of the same tag when the tag still points at the commit the run built, refuses to touch a tag that points anywhere else, and refreshes the title, the notes and the draft or prerelease state, so a re-dispatch is what publishes a release that was created as a draft.
- [FIX] The Windows release gate now runs at all. GitHub's Windows runners check out shell scripts with CRLF endings, and bash cannot parse them — `set -euo pipefail` becomes `set -euo pipefail\r` and the script dies on its first line — so the signed Windows tester release could never publish, while every check stayed green because the release path cannot be exercised from CI. `.gitattributes` now pins `*.sh` to LF endings, and the gate steps name the shell they use instead of relying on the runner's default. The gate also stopped treating any error that merely mentions a 404 as proof that the release tag does not exist: only GitHub's own answer, with its HTTP status, means the tag is absent, and the message is read apart from the response body, so a body that quotes someone else's 404 — or one that happens to carry a `status` field — can no longer be read as absence and let a release publish under a tag pointing at another commit. The wiring check compares the environment job by job, so a publishing job that loses its `environment:` key is caught even when another job in the same file still declares one. It also requires the gate to run as a command (a comment that names the script does not run it), to run before the release is published (a gate that runs afterwards cannot retract the release), to be the gate and nothing else (a step that swallowed the gate's exit status would stay green when the gate failed), to be a step that can fail the job at all (`continue-on-error` or a condition would let the release publish after the gate said no), and to run in the preflight as well as in the publishing job, so a broken environment is caught before a Windows runner is reserved.
- [SECURITY] The Windows signing release gate now names the environment it checks instead of defaulting to one, so a renamed environment can no longer be checked under the old name while the release published into an environment with no protection rules; `scripts/check-release-environment-wiring.sh`, run by `scripts/validate.sh`, keeps the name the check is given and the release job's `environment:` key from drifting apart, and proves it catches a drifted name. The gate also verifies that the environment declares `prevent_self_review` explicitly instead of leaving the platform default in force — this repository has one maintainer, so the value is reported rather than required to be true, because requiring it would leave every release unapprovable. A failed annotated-tag peel now stops the release with an error instead of a raw command failure, and `windows-tester-release.yml` gained a concurrency group so a second dispatch for the same tag waits instead of building again and failing on a release that already exists.
- [SECURITY] The Windows signing release workflows now publish only after a human approval in the `windows-release` environment, whose deployment branch policy admits only `refs/heads/main` and which no longer lets administrators bypass its protection rules; both preflights refuse a dispatch from any other branch, and the environment is checked again inside the publishing job — it has to exist, still require a reviewer, still name one, still carry a branch policy and still admit exactly `main` — so an environment that was deleted or unprotected in between cannot turn the gate into a no-op. `windows-tester-release.yml` validates its own `windows-tester-v<semver>` tag namespace and creates its release with `--target "$GITHUB_SHA"` — refusing when a tag of that name already points at a different commit — so the tag points at the commit that was actually built; `local-transcription-windows.yml` now refuses a pre-existing `transcription-windows-v<semver>` tag that points elsewhere the same way, instead of attaching the release to it. The preflights run with read-only permissions; only the publishing jobs get `contents: write`.
- [SECURITY] `scripts/validate.sh` now fails closed when it cannot diff against the base ref. The changed-file list comes from `scripts/changed-files.sh`, where git's exit status is no longer discarded by a process substitution, so a stale, missing or unrelated base ref can no longer produce a green Semgrep PASS while the scanner looked at no files; the shell and Python lint listings are captured with the same explicit error check. The helper falls back to a direct tree comparison when a shallow checkout has no merge base, so the gate keeps working in CI's shallow clones, and it keeps non-ASCII paths scannable. `scripts/check-changed-files.sh` pins the behaviour — the gate itself, not just the helper — and runs as part of the gate.
- [INTERNAL] The update-check parity matrix documents Windows-specific package selection and search limits instead of incorrectly claiming both ports still use the same latest-release endpoint.
- [FIX] Windows update checks search published releases for an uploaded app package matching the running x64 or ARM64 process, ignoring macOS and transcription-server releases, drafts and prereleases. Windows tester tags compare correctly; links stay on this repository, and missing packages or incomplete searches report an unknown result rather than claiming the app is up to date.
- [SECURITY] Windows encrypts saved session metadata, transcripts, review summaries and recording drafts using AES-GCM with per-file keys wrapped by current-user DPAPI. Legacy plaintext/BOM sessions remain readable and upgrade on save, including retained draft notes; explicit exports remain plaintext. Encryption failures do not fall back to plaintext writes.
- [FIX] Windows Jira exports preserve configured context paths, with or without a trailing slash, in both issue-creation requests and returned issue links.
- [FIX] Windows issue review now previews screenshot highlights and lets reviewers reposition them by dragging or keyboard arrows and remove them before saving or exporting. Edits preserve annotation metadata and stay inside the image bounds; missing images retain their annotations and offer named removal controls. Session bundles render the current annotations instead of copying stale cached highlights.
